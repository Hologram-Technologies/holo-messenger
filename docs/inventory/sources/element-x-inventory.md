## A. Architecture

**Layers (same shape on both).** matrix-rust-sdk is used through its generated bindings. UI code never touches them. iOS wraps them in proxy services (`ClientProxy`, `JoinedRoomProxy`, `TimelineProxy`, `RoomSummaryProvider`, `SecureBackupController`, `SessionVerificationControllerProxy`, `SpaceServiceProxy`). Android splits `libraries/matrix/api` (interfaces such as `MatrixClient`, `JoinedRoom`, `Timeline`) from `libraries/matrix/impl` (Rust-backed). Navigation sits above: iOS flow coordinators, each an explicit state machine (root, authentication, onboarding, session, chats, room, space, app lock) that builds screen coordinators; Android a tree of navigation nodes (`RootFlowNode` → `LoggedInFlowNode` → `RoomFlowNode` → `JoinedRoomLoadedFlowNode` → feature flows) with typed targets. Every screen is state in, events out: an iOS view model with a `ViewState` and `ViewAction` enum drawn by SwiftUI; an Android presenter emitting an immutable state with an event sink drawn by Compose.

**How the SDK reaches the UI.**
- Sliding sync: `SyncService` and `RoomListService` deliver the room list as diffs with dynamic filters, a loading state and a sync indicator. The UI reports the visible range so only those rooms are fully subscribed.
- Timeline: a per-room object emits item diffs, events plus virtual items (date dividers, read marker, start, pagination). Variants: live, event-focused, pinned, thread, media-only.
- Send queue: a send returns at once with a local echo and transaction ID. The SDK queue persists and retries; the UI reads send state per item and a queue-disabled signal. Media sends return a cancellable handle.
- Crypto stays inside the SDK. The UI sees verification, recovery and backup state, per-message shields, identity changes and typed send failures.
- Notifications are resolved in a separate process (iOS service extension, Android push handler) with the SDK's `NotificationClient`.

**Element Call.** A web app with observable view models over `@element-hq/matrixrtc-sdk`. Signalling is MatrixRTC: each device publishes a call membership in the room (state events, moving to sticky events) with a server-delayed leave; ringing is a notification event answered by joining or by a decline event. Media is WebRTC through a LiveKit SFU, frame-encrypted with per-participant keys sent over Matrix. Server-side parts: homeserver (membership, key transport, transport discovery, OpenID token), the MatrixRTC authorisation service that issues SFU tokens, and the SFU. Everything else (layouts, lobby, devices, reactions, ringing UI, frame encryption) is client-side.

**Embedding.** Both apps bundle the embedded build and load it in a WebView as a widget. The SDK widget driver grants a fixed capability set and relays messages, so the call app has no login of its own. The host supplies URL parameters, JS controls (picture-in-picture, audio devices), CallKit and PushKit on iOS, a foreground service and full-screen incoming activity on Android. Both carry an experimental native call stack behind a flag.

**matrix-rust-sdk concepts depended on.** Client and session restore; OAuth and QR login; SyncService; RoomListService and filters; Room and RoomInfo; Timeline diffs, focus, filter; send queue and handles; Encryption (recovery, backup, identity reset); session verification controller; user identities and shield state; NotificationClient; notification settings; pushers; SpaceService; thread list service; room directory search; search service; widget driver and capabilities provider; RTC notification and decline; live-location updates; composer drafts; media loader; room preview; knock requests; power levels.

## C. What this does not cover

- Nothing was built or run. Surface rows describe layout and gestures as read from view files, state and action types and coordinator state machines; fine visual behaviour (animations, exact thresholds, haptics, wording variants) is inferred from names and should be checked on a device before being treated as a requirement.
- View-model and presenter bodies were read selectively (call manager, notification extension, widget capability list, call ringing lifecycle). For most screens only the state/action/event contracts were read, so validation rules and edge-case branching inside them are not captured.
- Android: the room list filter set, home tabs, nav targets, timeline actions, slash commands, feature flags and event contracts were read; individual Compose views mostly were not. Items marked "not verified" in the table are the known gaps (link-safety prompt on iOS, history-sharing notice on Android, account provisioning link handling on Android, iOS appearance selector).
- `libraries/matrix/impl` (Android) and most iOS proxy implementations were sampled for SDK type usage, not read line by line. matrix-rust-sdk itself was not cloned; SDK concepts are named as the apps use them.
- Element Call: `sdk/src` internals (membership manager, connection map, key distribution) were read only through the architecture document and public interfaces; LiveKit server behaviour and the authorisation service are outside these repos. Keyboard shortcuts and desktop-only layouts were skipped as not phone-relevant.
- element-meta is thin and partly dated (2022 to 2023). Only first-run flow, trust decorations, key backup, device management, sign-out placement, message previews and default notification docs fed the table; its issue tracker and Figma links were not followed.
- Enterprise modules, accessibility test targets, localisation, analytics event catalogues, the macOS context menu and iPad pointer interactions were not inventoried.
- Feature-flag defaults were not checked, so "flagged" means a toggle exists, not that the feature is off in store builds.
